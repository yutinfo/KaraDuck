# แบบระบบ: ร้องเลย ออนไลน์ (Vercel + Firebase, หลายห้อง)

วันที่ 25 พ.ย. 2026 · สถานะ: รออนุมัติ · เอกสารที่เกี่ยวข้อง: `docs/DESIGN.md` (สัญญาเวอร์ชันในบ้าน), `docs/REVIEW.md` (ผลรีวิว รหัสข้อ A1–A12, B1–B6, C1–C6 ที่อ้างในเอกสารนี้), `spikes/vercel-yt-test/README.md` (ผลทดสอบ YouTube บน Vercel)

## 1. ทำไปเพื่ออะไร

ปีใหม่นี้จะมีสองบ้านร้องคาราโอเกะพร้อมกันผ่านเว็บตัวเดียวที่อยู่บนอินเทอร์เน็ต แต่ละบ้านต้องมีคิว จอหลัก และมือถือสั่งเพลงของตัวเอง
ไม่ปนกัน เจ้าของไม่อยากดูแลเซิร์ฟเวอร์หรือเปิดเครื่องที่บ้านทิ้งไว้ จึงเลือกวางบน Vercel และเก็บข้อมูลใน Firebase

เวอร์ชันปัจจุบันออกแบบมาใช้ในวง LAN: มีห้องเดียว และถือว่าคำขอจากเครื่องตัวเองคือเจ้าของห้อง (A1) ซึ่งใช้บนอินเทอร์เน็ตไม่ได้

## 2. เป้าหมาย สิ่งที่ไม่ทำ และสิ่งที่ห้ามเกิด

**เป้าหมาย**
- หลายห้องบนเว็บเดียว แต่ละห้องมีคิว ประวัติ สถานะตัวเล่น และรหัสแขกของตัวเอง
- สิทธิ์สองระดับต่อห้อง: เจ้าของ (จอหลัก) และแขก (มือถือ) ยืนยันด้วยโทเคน ไม่ดูจาก IP
- เจ้าของระบบ (คุณ) เป็นคนเดียวที่สร้างและลบห้องได้
- ทุกจอเห็นคิวเปลี่ยนภายในราว 1 วินาที เหมือนเวอร์ชันในบ้าน
- หน้าตาและวิธีใช้ของจอหลักกับมือถือเหมือนเดิม
- ยังรันบนเครื่องตัวเองได้ด้วยโค้ดชุดเดียวกัน (ใช้พัฒนา ทดสอบ และเป็นทางถอยถ้าออนไลน์มีปัญหา)
- ซ้อมสองห้องพร้อมกันบนของจริงได้ภายในกลางเดือนธันวาคม 2026

**ไม่ทำในรอบนี้**
- ระบบสมัครสมาชิกหรือล็อกอิน และการให้คนทั่วไปสร้างห้องเอง
- จอหลักหลายจอในห้องเดียวที่เล่นพร้อมกัน (ถ้าเปิดสองจอจะเล่นทั้งคู่เหมือนปัจจุบัน)
- รองรับห้องจำนวนมาก (ออกแบบไว้สำหรับไม่เกินราว 10 ห้อง)
- ทางสำรองด้วย YouTube Data API
- การแตกไฟล์หน้าเว็บขนาดใหญ่และรวมโค้ดซ้ำ (C1, C2, C4), B3, B4, B6

**ห้ามเกิด**
- คนของห้องหนึ่งอ่านหรือแก้คิวของอีกห้องได้
- ทำคำสั่งของเจ้าของได้โดยไม่มีโทเคนเจ้าของ
- ความลับ (กุญแจบริการ Firebase, กุญแจผู้ดูแล, ความลับที่ใช้เซ็นโทเคน) หลุดขึ้น git หรือไปอยู่ในหน้าเว็บ
- งานพัฒนาไปรบกวนเซิร์ฟเวอร์ที่บ้านซึ่งใช้ร้องเพลงอยู่ทุกวัน (พอร์ต 8791)

## 3. ข้อจำกัด

- ใช้แผนฟรีของ Vercel (Hobby) และ Firebase (Spark) ตัวเลขเพดานอยู่ในข้อ 12
- Node 22 ไม่มี dependency จาก npm และไม่มีขั้น build เหมือนเดิม
- ฟังก์ชันบน Vercel จำอะไรข้ามคำขอไม่ได้อย่างเชื่อถือได้ และไม่มีดิสก์ถาวร
- การค้นหาและการตรวจเพลงที่ฝังได้ใช้ช่องทางไม่เป็นทางการของ YouTube ทดสอบจาก Vercel สิงคโปร์แล้วผ่าน 84/84 ครั้ง แต่ยังไม่ได้พิสูจน์การใช้ต่อเนื่องทั้งคืน
- ใช้ส่วนตัวในครอบครัวเท่านั้น (แผน Hobby ของ Vercel ห้ามใช้เชิงพาณิชย์ และข้อตกลงของ YouTube ตาม A12)

## 4. ทางเลือกที่พิจารณา

| ทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. Vercel + Firebase Realtime Database (เลือก)** | ฟรี ไม่ต้องเปิดเครื่องหรือดูแลเซิร์ฟเวอร์ ได้ HTTPS และโดเมน | ต้องเขียนชั้นเก็บข้อมูลและชั้นส่งคิวสดใหม่ พึ่งบริการสองเจ้า |
| B. เครื่องที่บ้าน + tunnel + SQLite | แก้โค้ดน้อยสุด YouTube เห็นเป็น IP บ้าน | เครื่องต้องเปิดตลอดช่วงที่อีกบ้านเล่น |
| C. เช่า VPS | เปิดตลอด โค้ดใกล้ของเดิม | มีค่าเช่า ต้องดูแลเครื่องเอง |

เจ้าของเลือกทาง A เมื่อ 24 พ.ย. 2026 หลังการทดสอบ YouTube บน Vercel ผ่าน

การตัดสินใจย่อยภายในทาง A (ผมตัดสินแทน บอกได้ถ้าไม่เห็นด้วย):
- **Realtime Database ไม่ใช่ Firestore** เพราะข้อมูลเป็นก้อนเล็กก้อนเดียวต่อห้องและต้องการการแจ้งเปลี่ยนแปลงสด
- **คุยกับ Firebase ผ่าน REST ไม่ใช้ชุด SDK** ฝั่งฟังก์ชันเซ็นชื่อบัญชีบริการด้วย `node:crypto` ฝั่งหน้าเว็บฟังด้วย `EventSource` ที่ใช้อยู่แล้ว โปรเจกต์จึงยังไม่มี dependency และทดสอบด้วยการสอด `fetch` ปลอมได้เหมือนเทสต์เดิม ถ้าเบราว์เซอร์ฟัง Firebase ตรงไม่ได้ (ดูข้อ 13) ทางถอยคือโหลด Firebase SDK จาก CDN ของ Google มาใช้เป็นช่องรับข้อมูลเฉพาะตอนออนไลน์ (ดูข้อ 9)
- **โทเคนแบบเซ็นชื่อ (HMAC) ไม่เก็บรหัสในฐานข้อมูล** ตรวจได้โดยไม่ต้องอ่านฐานข้อมูล และไม่มีความลับอยู่ในข้อมูลที่หน้าเว็บอ่านได้
- **เลิกโหมด "เครื่องตัวเอง = เจ้าของ" ทุกที่** รวมทั้งตอนรันบนเครื่อง เพื่อให้มีระบบสิทธิ์แบบเดียว

## 5. ภาพรวม

```
จอหลัก / มือถือ (หน้าเว็บนิ่งบน Vercel)
   │  ฟังการเปลี่ยนแปลงของห้อง (EventSource, อ่านอย่างเดียว)
   ├───────────────────────────────────────────────► Firebase Realtime Database
   │                                                   rooms/<roomId>
   │  คำสั่ง ค้นหา ตรวจเพลง (HTTPS + Authorization: Bearer <โทเคน>)
   └──► ฟังก์ชันบน Vercel (สิงคโปร์) ──เขียนด้วยบัญชีบริการ──► Firebase
              └──► YouTube (ค้นหา, หน้า embed)
```

หน้าเว็บไม่เคยเขียน Firebase เอง ทุกการเปลี่ยนแปลงผ่านฟังก์ชัน ซึ่งใช้ตรรกะคิวเดิม (`public/js/store.js`, `public/js/commands.js`)

## 6. ข้อมูลใน Firebase

```
rooms/<roomId>/
  q : "<ข้อความ JSON>"      สถานะคิวทั้งก้อน
  p : { s: "playing" | "paused" | "buffering" | "idle",      สถานะตัวเล่นที่จอหลักรายงาน
        c: { a: "toggle" | "restart", t: <เวลา ms> } }       คำสั่งควบคุมล่าสุดจากมือถือ
```

`q` เมื่อแปลงกลับเป็นวัตถุ:
`{ rev, name, guestEpoch, ownerEpoch, current, queue, history }` โดย `current`, `queue`, `history` มีรูปเดิมตาม `store.js`

- `roomId`: 16 ตัวจากชุดอักษร `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` สุ่มด้วย `crypto`
- `q` เก็บเป็นข้อความก้อนเดียว เพราะ Realtime Database ไม่เก็บอาร์เรย์ว่างและค่า null การเก็บเป็นข้อความทำให้สถานะกลับมาเหมือนเดิมทุกตัวอักษร และใช้ ETag ตรวจการเขียนชนกันได้ตรงไปตรงมา
- `p` แยกจาก `q` เพื่อให้การรายงานสถานะตัวเล่นและการกดหยุด/เล่นไม่ต้องส่งคิวทั้งก้อนไปทุกจอ
- `playerState` ที่หน้าเว็บใช้ = `p.s` ถ้ามีเพลงปัจจุบัน ไม่งั้นเป็น `idle`
- คำสั่งควบคุม: ทุกครั้งที่ช่องฟังต่อติด (ครั้งแรกหรือต่อใหม่หลังหลุด) จอหลักจำค่า `p.c.t` ที่ได้มาเป็นฐานโดยไม่ทำตาม แล้วทำตาม `p.c.a` เฉพาะเมื่อ `t` เปลี่ยนระหว่างที่ยังต่ออยู่ คำสั่งที่กดตอนจอหลักหลับจึงไม่ถูกทำย้อนหลังตอนตื่น และไม่ต้องพึ่งนาฬิกาของเครื่อง

กฎความปลอดภัย (`database.rules.json`):

```json
{ "rules": { ".read": false, ".write": false,
             "rooms": { "$room": { ".read": true } } } }
```

ใครรู้ `roomId` อ่านคิวของห้องนั้นได้ แต่ไล่ดูรายชื่อห้องไม่ได้ และไม่มีใครเขียนได้นอกจากฟังก์ชัน (บัญชีบริการข้ามกฎ)
ข้อมูลที่อ่านได้มีแค่ชื่อเพลง ชื่อคนขอ และตัวนับรอบของโทเคน ไม่มีความลับ

## 7. สิทธิ์และโทเคน

รูปโทเคน: `<roomId>.<บทบาท><รอบ>.<ลายเซ็น>` เช่น `K7M2…Q9.g3.<22 ตัว>`
- บทบาท `o` = เจ้าของ, `g` = แขก · รอบ = เลขจำนวนเต็ม
- ลายเซ็น = 16 ไบต์แรกของ HMAC-SHA256(`ROOM_SECRET`, `<roomId>.<บทบาท><รอบ>`) เข้ารหัส base64url เทียบด้วย `timingSafeEqual`
- โทเคนใช้ได้เมื่อลายเซ็นถูก และรอบตรงกับ `guestEpoch` หรือ `ownerEpoch` ใน `q` ของห้องนั้น

| ใคร | ได้โทเคนอย่างไร | ทำอะไรได้ |
|---|---|---|
| ผู้ดูแลระบบ | กุญแจ `ADMIN_KEY` (อยู่ใน env ของ Vercel และเครื่องของคุณ) | สร้าง ลบ ดูรายชื่อห้อง ออกลิงก์เจ้าของใหม่ |
| เจ้าของห้อง | ลิงก์ `https://<เว็บ>/#o=<โทเคน>` ที่ผู้ดูแลส่งให้ทางช่องทางส่วนตัว | ทุกคำสั่งของห้อง รวมล้างคิว ล้างประวัติ รายงานสถานะตัวเล่น ดู QR แขก เปลี่ยนรหัสแขก |
| แขก | สแกน QR หรือเปิดลิงก์ `https://<เว็บ>/remote#g=<โทเคน>` | ทุกอย่างที่มือถือทำได้ในเวอร์ชันปัจจุบัน: ค้นหา เพิ่ม เล่นเลย ลบ ย้ายเพลง ข้ามเพลง หยุด/เล่น (ทุกคำสั่งยกเว้นรายการ "เฉพาะเจ้าของ" ในข้อ 8) |

- โทเคนอยู่หลัง `#` ของลิงก์ จึงไม่ถูกส่งไปเซิร์ฟเวอร์และไม่ลง log (แก้ A7) หน้าเว็บเก็บลง `localStorage` แล้วลบออกจากแถบที่อยู่ จากนั้นส่งในหัว `Authorization: Bearer` ทุกครั้ง
- "เปลี่ยนรหัสแขก" เพิ่ม `guestEpoch` ทีละหนึ่ง มือถือทุกเครื่องต้องสแกน QR ใหม่ แขกเก่ายังอ่านคิวได้ (เพราะรู้ `roomId`) แต่สั่งอะไรไม่ได้ ผมถือว่ายอมรับได้สำหรับใช้ในครอบครัว
- ลิงก์แขกต้องยาวไม่เกิน 100 ไบต์ เพราะตัวสร้าง QR (`lib/qr.mjs`) รองรับถึงรุ่น 6 ถ้าโดเมนยาวจนเกิน ต้องขยายตัวสร้าง QR

## 8. API

ทุกเส้นทางตอบ JSON ข้อผิดพลาดเป็น `{ "error": "<รหัส>" }` ตรวจโทเคนก่อนอ่านเนื้อคำขอ (แก้ A9) ไม่ใส่หัว CORS

| เส้นทาง | สิทธิ์ | หน้าที่ |
|---|---|---|
| `GET /api/config` | ไม่ต้อง | `{ mode: "cloud" \| "local", db, origin }` — `db` คือฐานที่อยู่สำหรับฟัง, `origin` คือที่อยู่เว็บที่ใช้สร้างลิงก์แขก |
| `GET /api/room` | แขก/เจ้าของ | `{ roomId, name, role }` เจ้าของได้เพิ่ม `{ guestUrl, qrSvg }` ใช้ตรวจโทเคนตอนเปิดหน้า |
| `POST /api/command` | ตามคำสั่ง | คำสั่งเดิมทั้งหมด + `rotateGuest` (เจ้าของ) ตอบ `{ ok: true, rev }` |
| `GET /api/search?q=` | แขก/เจ้าของ | เหมือนเดิม |
| `GET /api/embeddable?ids=` | แขก/เจ้าของ | เหมือนเดิม ส่ง `Referer` เป็นที่อยู่เว็บจริง |
| `POST /api/admin` | `ADMIN_KEY` | `{ action: "create", name }` → `{ roomId, ownerUrl }` · `list` · `delete` · `rotateOwner` |

คำสั่งเฉพาะเจ้าของ: `clearQueue`, `clearHistory`, `report`, `rotateGuest` (แขกได้ 403 `owner_only`)

ขั้นตอนของ `POST /api/command`:
1. ตรวจลายเซ็นโทเคน (401 `bad_token`) ตรวจชนิดเนื้อหาเป็น JSON (415) และขนาดไม่เกิน 16 KB (413)
2. อ่าน `q` พร้อม ETag ถ้าไม่มีห้อง → 404 `no_room` ถ้ารอบของโทเคนไม่ตรง → 401 `stale_token`
3. `control` → เขียน `p/c` · `report` → เขียน `p/s` · คำสั่งคิว → `applyCommand` แล้วเพิ่ม `rev`
4. คิวเกิน 200 เพลง → 409 `queue_full` (แก้ A3)
5. เขียน `q` แบบมีเงื่อนไข ETag ถ้าชนกับคำสั่งอื่นให้อ่านใหม่แล้วลองอีก สูงสุด 5 รอบ เกินนั้น → 503 `busy`

คำสั่งใหม่ `moveTo { qid, beforeQid | null }` ใช้กับการลาก: ย้ายเพลงไปไว้หน้าเพลงที่ระบุ (หรือท้ายคิว) จึงไม่ย้ายผิดตำแหน่งเมื่อคิวเปลี่ยนระหว่างลาก (แก้ B2) คำสั่ง `move { qid, delta }` คงไว้ให้ปุ่มลูกศร

## 9. หน้าเว็บ

- `sync.js` แบ่งเป็นสองชั้นตั้งแต่แรก: **ช่องรับข้อมูล** (ส่งข้อมูลห้องทั้งก้อนหรือการเปลี่ยนแปลงรายตำแหน่งขึ้นมา) และ **ตัวรวม** (รวมเป็นข้อมูลห้อง แล้วเรียก `onState` และ `onControl` ด้วยรูปข้อมูลเดิม) ตัวรวมเป็นฟังก์ชันล้วนที่มีเทสต์
- ช่องรับข้อมูลหลักคือ `EventSource` ไปที่ `<db>/rooms/<roomId>.json` รับเหตุการณ์ `put` และ `patch` (มี `path` และ `data`) ใช้ทั้งออนไลน์และบนเครื่อง ถ้าการลองในขั้นที่ 1 ไม่ผ่าน ให้เพิ่มช่องรับข้อมูลตัวที่สองที่ใช้ Firebase SDK เฉพาะโหมดออนไลน์ (บนเครื่องยังใช้ `EventSource`) และเพิ่ม `www.gstatic.com` ใน CSP
- คำสั่งส่งด้วยหัว `Authorization`
- สถานะใหม่ที่ต้องแสดง: โทเคนใช้ไม่ได้ ("สแกน QR ใหม่" บนมือถือ แก้ B5, "ขอลิงก์ห้องใหม่" บนจอหลัก), ห้องถูกลบ, เปิดหน้าโดยไม่มีโทเคน
- จอหลัก: เอา QR จาก `GET /api/room` แทน `/api/qr.svg` เพิ่มปุ่ม "คัดลอกลิงก์แขก" และ "เปลี่ยนรหัสแขก" ในแท็บมือถือ แสดงชื่อห้อง
- จอหลักส่ง `advance` ซ้ำแบบถอยเวลา (1, 2, 4… วินาที) จนกว่าจะเห็นเพลงปัจจุบันเปลี่ยน คำสั่งนี้ระบุ `qid` จึงส่งซ้ำได้โดยไม่ข้ามเพลงเกิน (แก้ B1)
- จอหลักหน่วงการรายงานสถานะตัวเล่นอย่างน้อย 1 วินาที เพื่อไม่ให้ช่วงโหลดวิดีโอสร้างคำขอถี่
- โหมด `?demo=1` คงเดิม

## 10. รันบนเครื่องตัวเอง

`node server.mjs` ใช้ตัวจัดการ API ชุดเดียวกับบน Vercel แต่สลับชั้นเก็บข้อมูลเป็นไฟล์ และจำลองช่องฟังของ Firebase

- ชั้นเก็บข้อมูลมีสองตัวที่มีหน้าตาเดียวกัน: `rtdb` (REST ไป Firebase) และ `file` (`data/rooms.json` เขียนแบบสลับไฟล์ ถ้าไฟล์เสียให้เก็บสำเนาไว้ก่อนเริ่มใหม่ แก้ A10)
- `GET /local-db/rooms/<roomId>.json` ส่งเหตุการณ์รูปแบบเดียวกับ Firebase จำกัด 50 การเชื่อมต่อ (แก้ A4) หน้าเว็บจึงใช้โค้ดเดียวกันทั้งสองโหมด
- ครั้งแรกที่รัน: สุ่ม `ROOM_SECRET` และ `ADMIN_KEY` เก็บใน `data/` (สิทธิ์ 0600) สร้างห้อง "บ้าน" ที่ว่างเปล่า แล้วพิมพ์ลิงก์เจ้าของ ไม่นำเข้าและไม่แตะ `data/state.json` ของเวอร์ชันเดิม
- ลิงก์แขกในโหมดนี้ใช้ที่อยู่ LAN ของเครื่อง ส่วน `Referer` ที่ส่งให้ YouTube ยังเป็น `http://localhost:<พอร์ต>/`
- ไฟล์ของ Vercel (`api/*.js`) เป็นตัวห่อบาง ๆ ที่เรียกตัวจัดการใน `lib/`

## 14. สิ่งที่เจ้าของต้องทำเอง

ผมจะเตรียมคำสั่งและไฟล์ให้ แต่ขั้นที่ใช้บัญชีหรือความลับของคุณต้องทำเอง:
1. สร้างโปรเจกต์ Firebase ด้วยบัญชี Google ของคุณ สร้าง Realtime Database ที่สิงคโปร์ วางกฎจาก `database.rules.json`
2. ออกกุญแจบัญชีบริการ แล้วใส่ค่าลงใน env ของโปรเจกต์ Vercel: `FIREBASE_DB_URL`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`
3. ตั้ง `ROOM_SECRET` และ `ADMIN_KEY` (สคริปต์ `tools/setup.mjs` สุ่มค่าและบอกคำสั่งให้)
4. สร้างห้องด้วย `node tools/room.mjs create "<ชื่อบ้าน>"` แล้วส่งลิงก์เจ้าของให้แต่ละบ้านทางช่องทางส่วนตัว

## 15. การทดสอบและเกณฑ์ผ่าน

- **เกณฑ์ผ่านสุดท้าย:** สองบ้านร้องพร้อมกันได้โดยคิวไม่ปนกัน และเซิร์ฟเวอร์ที่บ้านไม่ถูกรบกวนตลอดช่วงพัฒนา

## 16. ลำดับงานและสิ่งที่ปล่อยให้ผู้สร้างตัดสิน

1. **ลองของจริงกับ Firebase** (ต้องมีโปรเจกต์จากข้อ 14.1–14.2 ซึ่งยังไม่มี): เบราว์เซอร์ฟังตรงได้ไหม ฟังก์ชันบน Vercel เขียนแบบมีเงื่อนไขได้ไหม ฟังก์ชัน import ไฟล์จาก `public/js/` ได้ไหม ขั้นนี้ไม่ขวางขั้นที่ 2 เพราะหลังบ้านสร้างและทดสอบกับชั้นเก็บข้อมูลแบบไฟล์ได้ก่อน
2. **หลังบ้าน**: โทเคน ชั้นเก็บข้อมูลสองตัว ตัวจัดการ API เซิร์ฟเวอร์บนเครื่อง เครื่องมือผู้ดูแล เทสต์
3. **หน้าเว็บ**: ตัวซิงก์ การจัดการโทเคน QR และข้อมูลห้อง สถานะข้อผิดพลาด B1 B2 B5
4. **นำขึ้น**: `vercel.json` (ภูมิภาค หัวความปลอดภัย) กฎ Firebase ทดสอบสองห้อง
5. **ซ้อมและแก้** ภายในกลางเดือนธันวาคม

พัฒนาในสำเนาแยกของโปรเจกต์ ผมแนะนำให้ commit เวอร์ชันปัจจุบันเป็นฐานก่อนเริ่ม
