# ผลรีวิวโค้ด โครงสร้าง และความปลอดภัย

วันที่รีวิว: 2026-11-24 · ขอบเขต: โค้ดทั้งโปรเจกต์ ณ วันที่รีวิว (เทสต์ 83 ข้อผ่าน)
รีวิวอิสระ 3 ชุดแล้วรวมกัน: Claude (อ่านเซิร์ฟเวอร์ทั้งหมด + สแกนหน้าเว็บ), Codex (ความปลอดภัย สมมติว่าเปิดสู่อินเทอร์เน็ต), agy (โครงสร้างและคุณภาพโค้ด)
คอลัมน์ "ยืนยัน": ✔ = หัวหน้าอ่านโค้ดยืนยันเองแล้ว · ○ = มาจากผู้รีวิวคนเดียว ยังไม่ได้ยืนยันซ้ำ

## สรุป

- **ใช้ในบ้าน (LAN) ได้** ไม่พบช่องโหว่ที่คนนอกบ้านใช้ได้โดยตรง หน้าเว็บไม่มีจุดฝังสคริปต์ การเสิร์ฟไฟล์กัน path traversal ถูกต้อง
- **ยังไม่พร้อมเปิดสู่อินเทอร์เน็ต** เหตุผลหลักคือระบบสิทธิ์ผูกกับ "คำขอมาจากเครื่องตัวเอง" ซึ่งพังทันทีเมื่อวางหลัง reverse proxy หรือ tunnel และไม่มีการจำกัดการใช้ทรัพยากรเลย
- โครงสร้างพอดูแลได้ในขนาดนี้ แต่ไฟล์หน้าเว็บใหญ่และซ้ำกันมาก ควรจัดก่อนเพิ่มฟีเจอร์ใหญ่ถัดไป

**สิ่งที่ตรวจแล้วและทำถูก**
- Path traversal: ตรวจทั้ง path และ `realpath`; ขอ `data/state.json` / `.git/config` ได้ 404
- คำสั่งตรวจชนิดและขอบเขตข้อมูลครบ; ภาพปกสร้างจาก id ฝั่งเซิร์ฟเวอร์ ไม่เชื่อค่าจากลูกข่าย
- ไม่พบทาง XSS: หน้าใช้งานจริงใช้ `textContent` / DOM API ทั้งหมด ไม่มี inline script/style ใน HTML (พร้อมสำหรับ CSP แบบเข้ม)
- POST ต้องเป็น `application/json` และไม่มี CORS → ฟอร์มข้ามเว็บสั่งเปลี่ยนคิวไม่ได้
- ไม่มี SSRF: ปลายทางขาออกคงที่ที่ YouTube, id ถูกตรวจรูปแบบ, มี timeout
- ไฟล์สถานะสิทธิ์ `0600` เขียนแบบไฟล์ชั่วคราวแล้ว rename; `data/` ไม่ขึ้น git; สแกน 46 ไฟล์ที่จะขึ้น git ไม่พบความลับหรือรหัสห้องจริง
- ข้อความ error ไม่เปิดเผย stack trace

## D. แผนขึ้นออนไลน์แบบหลายห้อง (สองบ้านใช้เซิร์ฟเวอร์เดียว)

เป้าหมาย: แต่ละบ้านมีห้องของตัวเอง (คิว รหัส จอหลัก แยกกัน) บนเซิร์ฟเวอร์ออนไลน์ตัวเดียว ใช้ได้ทันปีใหม่

### สิ่งที่ต้องมีเพิ่ม
| สิ่งที่ต้องมี | จำเป็นไหม | หมายเหตุ |
|---|---|---|
| ที่รันเซิร์ฟเวอร์ตัวเดียวที่มีดิสก์ถาวร | จำเป็น | VPS เล็ก หรือเครื่องที่บ้านหนึ่งหลัง + tunnel; **ไม่ใช่** บริการ container ที่ดิสก์ชั่วคราว/หลายตัว (SSE และคิวในหน่วยความจำต้องอยู่โปรเซสเดียว) |
| ชื่อโดเมน + HTTPS | จำเป็น | reverse proxy ที่ออกใบรับรองให้เอง (เช่น Caddy) หรือ tunnel ที่ให้ HTTPS มาด้วย |
| ฐานข้อมูล | **ไม่ต้องมีบริการแยก** | ใช้ SQLite ที่มากับ Node 22 (`node:sqlite`, ทดสอบแล้วใช้ได้บนเครื่องนี้ ยังมีป้าย experimental) เก็บเป็นไฟล์เดียวบนดิสก์ — ยังไม่มี dependency เหมือนเดิม; ฐานข้อมูลแยก (Postgres/Redis) จำเป็นเมื่อจะรันหลายตัวพร้อมกันเท่านั้น |
| ระบบสิทธิ์ใหม่ | จำเป็น | แทน "มาจากเครื่องตัวเอง = เจ้าของ" ด้วยโทเคนเจ้าของห้อง + รหัสเข้าห้องของแขกที่แลกเป็น session |
| กุญแจผู้ดูแล (ตั้งใน env) | จำเป็น | ใช้สร้าง/ลบห้อง — ไม่เปิดให้ใครก็ได้สร้างห้อง เพื่อไม่ให้เซิร์ฟเวอร์ถูกใช้เป็นตัวค้น YouTube สาธารณะ |
| YouTube Data API key | ควรมีเป็นทางสำรอง | ถ้า IP ของเซิร์ฟเวอร์ถูก YouTube จำกัดช่องทางไม่เป็นทางการ; โควตาฟรีมีจำกัด ต้องพึ่งแคช |
| ตัวดูแลโปรเซส + log + สำรองข้อมูล | จำเป็น | systemd หรือเทียบเท่า, สำรองไฟล์ฐานข้อมูลรายวัน |

### ลำดับงาน
0. **ตัดสินใจและทดลอง (ครึ่งวัน)** — เลือกที่รัน (VPS หรือเครื่องที่บ้าน + tunnel) แล้ว**ทดสอบก่อนว่า IP นั้นค้นหาและตรวจเพลงกับ YouTube ได้** ข้อนี้เป็นความเสี่ยงอันดับหนึ่งของทั้งแผน ถ้าไม่ผ่านต้องใช้ Data API หรือรันที่บ้าน
1. **ห้องและสิทธิ์ (งานหลัก)** — แก้ A1, A6, A7 ไปในตัว
   - ห้อง: `rooms` (id, ชื่อ, โทเคนเจ้าของแบบ hash, รหัสเข้าห้อง, state JSON, เวลาใช้ล่าสุด) ใน SQLite; สถานะและ SSE แยกต่อห้อง
   - เส้นทาง: `/` = หน้ากรอกรหัสเข้าห้อง · `/r/<ห้อง>` = จอหลัก (ต้องมีโทเคนเจ้าของ) · `/j/<รหัส>` = ลิงก์ใน QR → แลกเป็น session cookie แล้วเข้าหน้าสั่งเพลง · `/api/r/<ห้อง>/…`
   - ผู้ดูแลสร้างห้องด้วยคำสั่ง (`node tools/room.mjs create "บ้านเรา"`) ได้ลิงก์จอหลักไปส่งให้แต่ละบ้าน
   - รหัสเข้าห้องเปลี่ยนใหม่ได้จากจอหลัก (เตะแขกเก่าออก)
2. **จำกัดทรัพยากรและ header** — A2–A5, A8–A10: เพดานคิว (200 เพลง/ห้อง), rate limit ต่อ IP และต่อห้อง, เพดาน SSE, ตรวจสิทธิ์ก่อนอ่าน body, ตรวจ `Host`/`Origin`, CSP + `nosniff` + `frame-ancestors`, รวมคำค้นซ้ำ, จำกัดขนาดคำตอบ, log ที่ไม่มีความลับ, เก็บไฟล์พังไว้กู้
3. **ความทนทานของหน้าเว็บ** — B1–B3, B5 (ลองเลื่อนคิวใหม่เมื่อล้มเหลว, คำนวณการลากจาก qid ปลายทางแทนระยะ, timeout ของตัวเล่น, หน้า "ลิงก์ใช้ไม่ได้")
4. **นำขึ้นจริงและซ้อม** — proxy/TLS, ตั้งให้เชื่อ header จาก proxy ตัวเดียว, สำรองข้อมูล, ซ้อมสองห้องพร้อมกันจากสองบ้านจริงก่อนปีใหม่อย่างน้อยหนึ่งครั้ง
5. **ทำทีหลังได้** — C1–C4 (จัดโครงสร้าง ลดโค้ดซ้ำ เทสต์หน้าเว็บ), B4, B6

### สิ่งที่ยังต้องตัดสินใจ
- รันที่ไหน: VPS (เปิดตลอด ไม่ผูกกับบ้านใด แต่เสี่ยงเรื่อง IP กับ YouTube) หรือเครื่องที่บ้านหนึ่งหลัง + tunnel (ฟรี ใช้ IP บ้าน แต่เครื่องนั้นต้องเปิดตอนอีกบ้านเล่น)
- แขกต้องใส่ชื่อไหม และเก็บประวัติข้ามคืนไหม (ข้อมูลส่วนบุคคลบนเซิร์ฟเวอร์สาธารณะ)
