# KaraDuck — ผลรีวิวโค้ด โครงสร้าง และความปลอดภัย

รายการเดิมมาจากรีวิววันที่ 24 พ.ย. 2026 โดย Claude, Codex และ agy
ตารางคงรหัสและประเด็น A1–A12, B1–B6, C1–C6 ไว้ และตรวจสถานะจากโค้ดใหม่ทีละข้อ ณ 25 พ.ย. 2026
เรื่องเดิมเป็นบริบทของสิ่งที่เคยพบ ไม่ใช่คำอธิบายว่าระบบปัจจุบันยังทำเช่นนั้นทั้งหมด
“ยังไม่แก้” รวมกรณีมีมาตรการแล้วบางส่วนแต่ยังเหลือปัญหาเดิม ไม่ได้หมายความว่าไม่มีการเปลี่ยนแปลง
ผลนี้เป็นการอ่านโค้ดและเทสต์ในโครงการ ไม่ใช่หลักฐานว่าทดสอบระบบ production หรือซ้อมใช้งานจริงแล้ว

ปัจจุบันใช้โทเคนแยกบทบาทและห้องแทนสิทธิ์จาก IP มีเพดานคิวและการสร้างห้อง
ระบบออนไลน์ใช้ Vercel กับ Firebase Realtime Database ส่วนบนเครื่องยังใช้ไฟล์และ SSE
ความเสี่ยงหลักที่ยังอยู่คือการใช้ทรัพยากรจากคนนอก ช่องทาง YouTube ที่ไม่เป็นทางการ และงานหน้าเว็บที่ยังไม่มีเทสต์ครอบคลุม

## D. แบบและแผนออนไลน์

ระบบหลายห้องใช้งานผ่าน Vercel และ Firebase แล้ว แบบย้อนหลังอยู่ใน [docs/specs/](specs/) โดยอ่าน [แบบหลัก](specs/2026-11-25-online-design.md) คู่กับ [ส่วนสร้างห้องสาธารณะและ PIN](specs/2026-11-25-public-rooms.md) สัญญาที่ตรงโค้ดปัจจุบันอยู่ใน [DESIGN](DESIGN.md) เอกสารแบบเป็นบันทึก ไม่ใช่หลักฐานว่างาน deploy และซ้อมผ่านแล้ว

ผู้ดูแลสร้างห้องได้ข้ามเพดานและสวิตช์สาธารณะ จึงต้องดูจำนวนห้องจริงแม้ปิดรับสร้างแล้ว

ก่อนใช้ต่อเนื่องควรซ้อมสองห้องคนละเครือข่ายอย่างน้อยหนึ่งชั่วโมง ค้นรวมอย่างน้อย 100 ครั้ง มือถือผ่านเน็ตมือถือ
ตรวจเปลี่ยนรหัส/ออกลิงก์เจ้าของใหม่ ปิดห้องขณะจอเปิด จอหลักหลับแล้วตื่น เครือข่ายหลุดแล้วต่อใหม่ และไม่เล่น control ย้อนหลัง
ตรวจ CSP/CORS ในเบราว์เซอร์ ตรวจฐานข้อมูลว่ารากและ meta อ่านไม่ได้ แล้วดูการใช้ Vercel/Firebase หลังซ้อม
การอ่านโค้ดรอบนี้ไม่ได้ยืนยันว่ากฎ Firewall หรือการซ้อมเหล่านี้ทำบน production แล้ว

## จุดที่โค้ดกับแบบต่างกัน

- แบบหลักกำหนดให้ผู้ดูแลสร้างห้อง ส่วนเพิ่มสาธารณะและ PIN ยกเลิกข้อนั้นแล้ว โค้ดรองรับส่วนเพิ่มทั้งสอง ไม่ใช่ข้อบกพร่องของโค้ด
- admin list คืน pin เพิ่มจากฟิลด์ที่แบบสาธารณะระบุ (`lib/handlers.mjs`) และเอกสารแบบ PIN ระบุเพิ่ม pin เฉพาะ owner room
- อย่าตีความ “ไม่มีการใช้งาน 24 ชั่วโมง” ว่ารวมทุกกิจกรรม โค้ดและรายละเอียดแบบนับเฉพาะการเขียน q ไม่มีการลบตามเวลาทันที
