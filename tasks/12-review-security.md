# ใบงาน 12 — รีวิวความปลอดภัย (อ่านอย่างเดียว)
ผู้รับงาน: Codex · โมเดล: gpt-6.1-sol / high · sandbox: read-only

## บริบท
แอปคาราโอเกะ Node 22 ไม่มี dependency: `server.mjs` + `lib/*.mjs` เสิร์ฟ `public/` และ API (`/api/search`, `/api/embeddable`, `/api/state`, `/api/events` (SSE), `/api/command`, `/api/remote-info`, `/api/qr.svg`)
ออกแบบมาใช้ในบ้าน (LAN): คำขอจาก loopback = เจ้าของห้อง ไม่ต้องมีรหัส; เครื่องอื่นต้องมีรหัสห้อง 6 ตัวใน `?k=`
**เจ้าของตั้งใจจะนำขึ้นออนไลน์ (เข้าถึงจากอินเทอร์เน็ต) และกำลังจะ push ขึ้น git** — ให้รีวิวด้วยสมมติฐานว่ามีผู้ไม่หวังดีเข้าถึงพอร์ตนี้ได้ และอาจถูกวางหลัง reverse proxy / tunnel
สัญญาและเหตุผลการออกแบบอยู่ใน `docs/DESIGN.md`

## สิ่งที่ต้องทำ
อ่านโค้ดจริง (ห้ามเดาจากชื่อไฟล์) แล้วรายงานช่องโหว่และจุดอ่อน ครอบคลุมอย่างน้อย:
1. การยืนยันตัวตน/สิทธิ์: โมเดล loopback = เจ้าของ, รหัสห้อง (ความยาว การเดา การหมุนเวียน การรั่วทาง URL/log/Referer), คำสั่งที่แต่ละฝั่งทำได้, ผลของ reverse proxy, DNS rebinding, ตรวจ `Host`/`Origin`
2. CSRF / CORS / คำขอข้ามเว็บ รวมถึง GET ที่มีผลข้างเคียง (ยิงออกไป YouTube)
3. การใช้ทรัพยากรและ DoS: ขนาดคิว/สถานะ, การเขียนไฟล์แบบ sync, จำนวน SSE, body/URL, แคช, การขยายคำขอขาออก (`/api/search`, `/api/embeddable`), ไม่มี rate limit
4. การเสิร์ฟไฟล์: path traversal, symlink, ไฟล์ที่ไม่ควรถูกเสิร์ฟ (ดู `public/` ทั้งหมด รวม `public/_mockup/`), header ความปลอดภัย (CSP, nosniff, frame-ancestors, Referrer-Policy)
5. การตรวจอินพุตของคำสั่ง (`public/js/commands.js`, `store.js`) และข้อมูลที่ไหลไปถึงหน้าเว็บ (XSS ผ่านชื่อเพลง/ชื่อคนขอ/ผลค้นหา) — ดูฝั่ง `public/js/app.js`, `remote.js` ว่ามี sink อันตรายไหม
6. คำขอขาออก: SSRF, การตรวจ id, timeout, ขนาดคำตอบ, การแปลผล HTML/JSON จาก YouTube
7. การเก็บข้อมูล: `data/state.json` (สิทธิ์ไฟล์, ความเสียหายจากไฟล์พัง, ข้อมูลส่วนบุคคล), ความลับที่อาจหลุดขึ้น git (ดู `.gitignore` และทุกไฟล์ที่ไม่ถูก ignore — รวม `tasks/`, `docs/`, `test/fixtures/`)
8. การจัดการ error/การล่มของโปรเซส, การ log
9. ความเสี่ยงด้านข้อตกลงการใช้บริการเมื่อเปิดสาธารณะ (การเรียก InnerTube ที่ไม่เป็นทางการ, การดึงหน้า embed) — ระบุสั้น ๆ พอ

## รูปแบบคำตอบ (ตอบในข้อความสุดท้าย ห้ามเขียน/แก้ไฟล์ใด ๆ)
ตารางหรือรายการ เรียงจากร้ายแรงสุด แต่ละข้อมี:
`[ระดับ: วิกฤต | สูง | กลาง | ต่ำ] ชื่อสั้น — ไฟล์:บรรทัด — สถานการณ์โจมตี/ผลกระทบ (รูปธรรม) — วิธีแก้ที่แนะนำ (สั้น) — เกี่ยวเฉพาะตอนออนไลน์ หรือกระทบตอนใช้ในบ้านด้วย`
แยกท้ายรายงาน: "สิ่งที่ตรวจแล้วและเห็นว่าทำถูก" (สั้น ๆ) และ "สิ่งที่ไม่ได้ตรวจ"
อย่ารายงานข้อที่ยืนยันจากโค้ดไม่ได้ว่าเป็นปัญหาจริง — ถ้าไม่แน่ใจให้ระบุว่า "ต้องยืนยัน" พร้อมเหตุผล
