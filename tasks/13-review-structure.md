# ใบงาน 13 — รีวิวโครงสร้างและคุณภาพโค้ด (อ่านอย่างเดียว)
ผู้รับงาน: agy · โมเดล: gemini-4-neon-high · mode: plan

**ห้ามแก้หรือสร้างไฟล์ใด ๆ และไม่ต้องเขียนแผน — ตอบเป็นข้อความรายงานอย่างเดียว**

## บริบท
แอปคาราโอเกะจาก YouTube: Node 22 ไม่มี dependency ไม่มี build
- เซิร์ฟเวอร์: `server.mjs`, `lib/app.mjs`, `lib/youtube.mjs`, `lib/qr.mjs`
- หน้าเว็บ: `public/index.html` + `styles.css` + `js/app.js` (จอหลัก), `public/remote.html` + `remote.css` + `js/remote.js` (มือถือ), ใช้ร่วม: `tokens.css`, `js/store.js`, `commands.js`, `sync.js`, `api.js`, `player.js`, `drag-sort.js`, `demo-data.js`
- เทสต์: `test/*.test.mjs` (`node --test`) · สัญญา: `docs/DESIGN.md` · ใบงานที่ผ่านมา: `tasks/`
โค้ดเขียนโดยหลายคนใน 6 รอบสั้น ๆ เจ้าของกำลังจะ push ขึ้น git และตั้งใจนำขึ้นออนไลน์ จึงอยากรู้ว่าโครงสร้างพร้อมให้ดูแลต่อหรือยัง

## สิ่งที่ต้องทำ
อ่านโค้ดจริงทุกไฟล์ข้างบน แล้วรายงาน:
1. **โครงสร้างโปรเจกต์และการแบ่งชั้น**: การแบ่งหน้าที่ของแต่ละไฟล์เหมาะไหม; โค้ดที่ใช้ร่วมเซิร์ฟเวอร์–เบราว์เซอร์ (`lib/app.mjs` import จาก `public/js/`) ควรอยู่ที่ไหน; ไฟล์ที่ใหญ่เกิน (`app.js`, `styles.css`, `remote.js`) ควรแตกอย่างไร — เสนอโครงเป้าหมายเป็นรายการไฟล์
2. **โค้ดซ้ำ**: ระหว่าง `app.js` กับ `remote.js` (toast, การสร้างแผ่นปก/แถวคิว, ปุ่มสองจังหวะ, ไอคอน SVG, การตรวจเพลงที่ฝังไม่ได้) และระหว่าง `styles.css` กับ `remote.css` — ระบุชิ้นที่ซ้ำพร้อมบรรทัด และเสนอโมดูล/ไฟล์กลาง
3. **บั๊กและกรณีขอบที่อ่านเจอ**: race condition (SSE มาระหว่างรอคำสั่ง, ค้นหาซ้อน, ลากคิวระหว่าง state เปลี่ยน), การล้าง timer/listener, สถานะที่ค้างได้ (เช่น คำสั่ง `advance` ตอนเพลงจบล้มเหลวแล้วไม่ลองใหม่), การจัดการ error ที่เงียบเกินไป — ระบุไฟล์:บรรทัดและสถานการณ์ที่ทำให้เกิด
4. **ความปลอดภัยฝั่งหน้าเว็บ**: จุดที่ใส่ข้อมูลจากภายนอกลง DOM (ต้องเป็น `textContent`/`setAttribute` เท่านั้น), URL รูป, การใช้ `localStorage`, ความพร้อมสำหรับ Content-Security-Policy แบบเข้ม (มี inline script/style/handler ไหม), `public/_mockup/glass.html` ควรถูกเสิร์ฟไหม
5. **คุณภาพเทสต์**: อะไรถูกทดสอบดีแล้ว อะไรสำคัญแต่ยังไม่มีเทสต์ (เรียงตามความเสี่ยง 5 อันดับ)
6. **ความพร้อมขึ้น git**: ไฟล์ที่ไม่ควรอยู่ใน repo หรือควรย้าย (`tasks/`, `public/_mockup/`, fixture), สิ่งที่ขาด (README, LICENSE, `.editorconfig`, คำสั่ง lint), ชื่อไฟล์/โฟลเดอร์ที่ชวนสับสน
7. **การเข้าถึง (accessibility) และประสิทธิภาพ** เฉพาะจุดที่เป็นปัญหาจริง (เช่น render ทั้งรายการใหม่ทุก state, `backdrop-filter` จำนวนมาก)

## รูปแบบคำตอบ
รายการเรียงตามความสำคัญ แต่ละข้อ: `[ระดับ: สูง | กลาง | ต่ำ] ชื่อสั้น — ไฟล์:บรรทัด — ปัญหา/สถานการณ์ — ข้อเสนอ (สั้น) — ขนาดงานโดยประมาณ (เล็ก/กลาง/ใหญ่)`
ท้ายรายงาน: "สิ่งที่ทำได้ดีแล้ว" (สั้น ๆ) และ "สิ่งที่ไม่ได้ตรวจ"
รายงานเฉพาะสิ่งที่ยืนยันได้จากโค้ด ถ้าไม่แน่ใจให้เขียนว่า "ต้องยืนยัน" · ไม่ต้องรันคำสั่งใด ๆ นอกจากอ่านไฟล์
